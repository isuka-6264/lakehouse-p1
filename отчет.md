## 2. Поднятые сервисы — и почему именно они

Проверено через `docker ps`: работают `lakehouse-minio`, `lakehouse-pg`, `lakekeeper`, `trino`; Spark запускается одноразовым контейнером (`docker run --rm`).

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| MinIO | S3-совместимое объектное хранилище, сюда физически падают parquet-файлы (бакеты `bronze`, `silver`, `gold`, `bench`) | Полностью совместим с API Amazon S3: тот же код и те же настройки (`s3.endpoint`, path-style) будут работать с настоящим S3 в облаке. Лёгкий (один контейнер), есть веб-консоль для проверки файлов. Альтернатива HDFS тяжелее (NameNode/DataNode) и не является стандартом для lakehouse. |
| PostgreSQL | БД, где Lakekeeper хранит метаданные каталога (namespace, таблицы, указатель на текущий metadata.json) | Надёжная транзакционная БД — каталогу нужна атомарная смена указателя на снапшот, иначе возможны потерянные коммиты. Официально поддерживается Lakekeeper, open source, разворачивается одной командой. |
| Lakekeeper | Iceberg REST Catalog — каталог метаданных таблиц, раздаёт движкам доступ к warehouse | Реализует открытую спецификацию Iceberg REST, поэтому к одним и тем же таблицам подключаются разные движки (в работе — Trino и Spark) без экспорта данных. Поддерживает несколько warehouse (по одному на слой медальона), написан на Rust — лёгкий. Альтернативы: Hive Metastore (устаревший Thrift-протокол, нужен Hadoop-стек), Nessie (хорош для git-ветвления данных, но для учебной задачи избыточен), AWS Glue (только облако). |
| Trino | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в MinIO; выполняет все ELT-шаги (CTAS, MERGE, ALTER) | Распределённый MPP-движок для интерактивного SQL: быстрый старт, ответы за секунды. Полная поддержка Iceberg (CTAS, MERGE, UPDATE, schema evolution, time travel, rollback, системные таблицы `$files`/`$snapshots`/`$partitions`). Встроенный коннектор `tpch` генерирует данные — ничего не скачиваем. Запущен с `-Xmx2G`, чтобы уложиться в память машины (см. §2, скрипты). |
| Spark 3.5.3 (+ Iceberg 1.7.1) | Второй движок: читает Bronze-слой через тот же REST-каталог (часть 2, §6.2) | Стандарт для batch-ETL; показывает главное свойство lakehouse — открытый формат: таблицы, записанные Trino, читаются другим движком напрямую. |

### Скрипты, которыми поднимал стек

Команды для Windows PowerShell (Docker Desktop, WSL 2), выполнялись из папки `C:\Users\Luna\lakehouse`.

```powershell
# 1. MinIO — объектное хранилище (консоль :9001, S3 API :9000)
#    Используется образ quay.io/minio/minio:latest, скачанный ранее.
#    Для новой установки — свободный форк pgsty/silo:latest (тот же интерфейс).

  -v minio-data:/data `
  quay.io/minio/minio:latest server /data --console-address ":9001"

# 2. PostgreSQL — хранилище метаданных Lakekeeper
docker run -d --name lakehouse-pg `
  -e POSTGRES_PASSWORD=postgres -p 5432:5432 `
  -v pg-data:/var/lib/postgresql/data `
  postgres:17

# 3. Lakekeeper — миграции БД (один раз), затем сам REST-каталог на :8181
docker run --rm `
  -e 'LAKEKEEPER__PG_ENCRYPTION_KEY=This-is-NOT-Secure!' `
  -e 'LAKEKEEPER__PG_DATABASE_URL_READ=postgresql://postgres:postgres@host.docker.internal:5432/postgres' `
  -e 'LAKEKEEPER__PG_DATABASE_URL_WRITE=postgresql://postgres:postgres@host.docker.internal:5432/postgres' `
  quay.io/lakekeeper/catalog:latest-main migrate

docker run -d --name lakekeeper `
  -e 'LAKEKEEPER__PG_ENCRYPTION_KEY=This-is-NOT-Secure!' `
  -e 'LAKEKEEPER__PG_DATABASE_URL_READ=postgresql://postgres:postgres@host.docker.internal:5432/postgres' `
  -e 'LAKEKEEPER__PG_DATABASE_URL_WRITE=postgresql://postgres:postgres@host.docker.internal:5432/postgres' `
  -p 8181:8181 `
  quay.io/lakekeeper/catalog:latest-main serve

# 4. Бакеты bronze/silver/gold/bench в MinIO (консоль или mc) и по warehouse на каждый слой
#    в Lakekeeper: POST /management/v1/warehouse с JSON вида config/warehouse-bronze.json
#    (поля warehouse-name и bucket = имя слоя). Пример для bronze:
curl.exe -X POST http://localhost:8181/management/v1/warehouse `
  -H "Content-Type: application/json" -d '@warehouse-bronze.json'

# 5. Trino — SQL-движок на :8080; каталоги bronze/silver/gold/tpch — файлы в папке catalog\
#    -Xmx2G: ограничение кучи JVM. Без него Trino занимает ~80 % памяти Docker,
#    и при серии записей машина с 7,6 ГБ RAM уходила в своп (Docker Engine зависал).
docker run -d --name trino `
  -p 8080:8080 `
  -v "${PWD}\catalog:/etc/trino/catalog" `
  -e JAVA_TOOL_OPTIONS="-Xmx2G" `
  trinodb/trino:476

# 6. Spark (одноразовый запуск) — читает Bronze через тот же Lakekeeper
docker run --rm `
  -v "${PWD}\spark\conf:/opt/spark/conf" `
  -v "${PWD}\spark\jars:/opt/spark/iceberg-jars" `
  -v "${PWD}\p1\sql:/opt/sql" `
  apache/spark:3.5.3 `
  /opt/spark/bin/spark-sql --driver-memory 1g -f /opt/sql/08_spark_bronze.sql
```

Файлы каталогов Trino (`catalog/bronze.properties` и аналогичные для silver/gold) — в папке `config/` репозитория; генератор данных — `catalog/tpch.properties` с одной строкой `connector.name=tpch`.

## 3. Разбор запроса — какие данные нужны

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
|---|---|---|
| `lineitem` | `orderkey`, `returnflag`, `extendedprice`, `discount` | `returnflag = 'R'` — фильтр (только возвращённые позиции); `orderkey` — джойн с `orders`; `extendedprice * (1 - discount)` — агрегат `sum(...) AS revenue` |
| `orders` | `orderkey`, `custkey`, `orderdate` | `orderdate ∈ [1993-10-01, 1994-01-01)` — фильтр по 4-му кварталу 1993; `orderkey` — джойн с `lineitem`, `custkey` — джойн с `customer` |
| `customer` | `custkey`, `name`, `acctbal`, `address`, `phone`, `comment`, `nationkey` | `custkey` — джойн и ключ группировки; `nationkey` — джойн с `nation`; остальные — вывод (и ключи `GROUP BY`) |
| `nation` | `nationkey`, `name` | Джойн по `nationkey`; `name` — вывод (страна клиента) |

Итог: сортировка по `revenue DESC`, `LIMIT 20`.

## 4. Медальон — решения по каждому слою

Общие решения для всех слоёв:
- **Формат PARQUET** — колоночный, читается только нужными колонками; стандарт экосистемы (Trino, Spark и любые другие движки читают его через Iceberg).
- **Сжатие ZSTD** — по результатам бенчмарка §5: размер почти как у GZIP (188 vs 183 МБ), при этом запись и запрос быстрее всех кодеков. Это также кодек по умолчанию в Iceberg/Trino.
- **Каждый слой — отдельный warehouse и бакет** (`bronze`, `silver`, `gold`), таблицы — в схеме `q10`. Слои изолированы: можно по-разному назначать права и политику хранения.

Размеры — сумма `file_size_in_bytes` из системной таблицы Iceberg `"<table>$files"`, строки — `count(*)`.

## 5. Тесты производительности

**Методика.**
- Bronze пересоздан 4 раза (отдельные схемы `bronze.bench_none|snappy|gzip|zstd`, скрипты `sql/04_bench_*.sql`), формат везде PARQUET, кодек задаётся `SET SESSION bronze.compression_codec`.
- **Время записи** — 4 CTAS из `tpch.sf1` подряд, замер `Measure-Command`.
- **Время запроса** — Q10 (`sql/05_q10_template.sql`) на соответствующем Bronze. Перед каждым кодеком перезапускаются Trino и MinIO (сброс кэша метаданных Trino и страничного кэша) → 1-й прогон «холодный», 2-й и 3-й — «тёплые».
- Каждый прогон проверен: вернул 20 строк. Время включает старт CLI внутри контейнера (~1 с, одинаково для всех кодеков).
- Размер — сумма `file_size_in_bytes` по 4 таблицам.
- Сырые результаты: `results/bench_write.csv`, `results/bench_size.csv`, `results/bench_q10.csv`.

| Сжатие на Bronze | Время записи, с | Время запроса Q10: холодный, с | Время запроса Q10: тёплые, с | Размер Bronze, МБ | Сжатие vs NONE | Твой вывод (что лучше и почему) |
|---|---|---|---|---|---|---|
| NONE | 27,3 | 10,00 | 7,02 / 6,94 | 489,6 | 1,0× | Худший по всем метрикам: на диск и из диска гоняется в 2,6× больше байтов. Даже запись медленнее, чем со сжатием — узкое место машины ввод-вывод, а не CPU. |
| SNAPPY | 16,8 | 7,85 | 5,37 / 5,18 | 259,4 | 1,9× | Быстрое, но слабое сжатие: файлы на 38 % больше, чем у ZSTD, поэтому и запрос медленнее. |
| **GZIP** | 25,9 | 6,98 | 4,05 / 3,48 | **183,2** | **2,7×** | Самый компактный, но запись в 1,7 раза дольше ZSTD (тяжёлый для CPU кодек). Оправдан для архивных, редко записываемых данных. |
| **ZSTD** | **15,0** | **6,87** | **3,95 / 3,29** | 188,3 | 2,6× | **Лучший компромисс:** размер всего на 3 % больше GZIP, при этом самая быстрая запись и самый быстрый запрос. Выбран для всех слоёв. |

**Выводы.**
1. **Чем меньше данные — тем быстрее запрос.** На этой машине узкое место — чтение байтов (диск, сеть до MinIO), а не CPU, поэтому распаковка окупается: GZIP/ZSTD читаются на 30 % быстрее NONE в холодном режиме и в 2 раза быстрее в тёплом.
2. **GZIP vs ZSTD:** почти одинаковый размер (183,2 vs 188,3 МБ), но ZSTD пишет в 1,7 раза быстрее (15,0 vs 25,9 с) и не уступает в скорости чтения. Для слоя, который регулярно перезаписывается (Bronze/Silver), выигрыш ZSTD в записи важнее 5 МБ экономии GZIP.
3. **Кэш:** тёплые прогоны на 30–50 % быстрее холодных (кэш метаданных Iceberg в Trino + страничный кэш ОС). Поэтому честное сравнение — по холодному прогону, и перед каждым кодеком стек перезапускался.
4. **Оговорка:** NONE записывался первым, его время может включать прогрев JVM Trino; вывод о «самой медленной записи» верен с этой поправкой. На sf1 данные малы, разница между кодеками на sf10+ будет больше.
5. **«В деньгах»:** ZSTD экономит 61 % места относительно NONE (301 МБ на 490 МБ). При цене объектного хранилища ~$0,02–0,03 за ГБ·мес. на sf1 это копейки, но на петабайтах — тысячи долларов в месяц.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Обычная OLTP-БД (PostgreSQL) хранит данные построчно на дисках одного сервера: хорошо для транзакций, плохо для аналитики по миллиардам строк, и масштабируется дорого (вертикально). Классическое DWH (Teradata, Vertica) быстрое, но дорогое и закрытое: данные в собственном формате, доступны только его движку. Data lake (файлы в S3) дешёв и масштабируется горизонтально, но без транзакций, схемы и истории превращается в «болото». **Lakehouse объединяет:** данные лежат в дешёвом объектном хранилище в открытом колоночном формате (Parquet), а табличный формат Iceberg добавляет транзакции (ACID), схему и её эволюцию, снапшоты и time travel. Хранение отделено от вычислений: в этой работе одни и те же таблицы читали **два разных движка** (Trino и Spark) без копирования — каждый движок масштабируется отдельно, и нет привязки к вендору. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | Скрипт `sql/06_schema_evolution.sql`, таблица `silver.q10.customer_enriched`. (1) `ALTER TABLE ... ADD COLUMN mktsegment varchar` — у всех 150 000 старых строк колонка читается как NULL, **число файлов данных не изменилось (1 → 1)**. (2) `MERGE INTO ... USING bronze.q10.customer` — колонка заполнена из Bronze (`MERGE: 150000 rows`, например `BUILDING`, `AUTOMOBILE`). (3) `RENAME COLUMN phone TO phone_number` и обратно — данные читаются под новым именем. В `$snapshots` после всего этого только `append` (исходная загрузка) и `overwrite` (MERGE): **ADD COLUMN и RENAME не создали снапшотов** — это изменения только метаданных. Так происходит потому, что Iceberg адресует колонки по уникальному ID, а не по имени или позиции: новая колонка получает новый ID, которого нет в старых файлах (→ NULL), а переименование лишь меняет имя у того же ID. |
| Пример скрипта восстановления данных из снапшота (time travel) | Скрипт `sql/07_time_travel.sql` (имитация ошибки и восстановления) — см. ниже. Результат: `UPDATE: 5948 rows`; сумма `acctbal` клиентов из JAPAN: сейчас **0,00**, `FOR VERSION AS OF` снапшот до ошибки — **26 898 468,71**; после `rollback_to_snapshot` — снова **26 898 468,71**. |

```sql
-- id снапшота до ошибки берём из истории:
SELECT committed_at, snapshot_id, operation
FROM silver.q10."customer_enriched$snapshots" ORDER BY committed_at;
-- -> 2358026435400632268

-- 1. «Ошибочное» изменение: обнулили баланс всех японских клиентов
UPDATE silver.q10.customer_enriched SET acctbal = 0 WHERE nation_name = 'JAPAN';

-- 2. Time travel: сравниваем текущее состояние с прошлым снапшотом
SELECT 'now' AS version, sum(acctbal) FROM silver.q10.customer_enriched
WHERE nation_name = 'JAPAN'
UNION ALL
SELECT 'before', sum(acctbal) FROM silver.q10.customer_enriched
FOR VERSION AS OF 2358026435400632268 WHERE nation_name = 'JAPAN';

-- 3. Восстановление: откат таблицы на снапшот до ошибки
ALTER TABLE silver.q10.customer_enriched
EXECUTE rollback_to_snapshot(2358026435400632268);

-- 4. Проверка
SELECT sum(acctbal) FROM silver.q10.customer_enriched WHERE nation_name = 'JAPAN';
```

### 6.2. Подключить инструмент к lakehouse

| Инструмент | Почему выбрал именно его |
|---|---|
| **Apache Spark 3.5.3** + Iceberg 1.7.1 (движок) | (1) Это главный batch-движок для ETL — в реальном lakehouse Trino обычно отвечает за интерактивные запросы, а Spark за тяжёлые пайплайны, и работа показывает, что они делят одни таблицы. (2) Подключается к **тому же REST-каталогу Lakekeeper** — никакой интеграции «под» Trino не нужно, это проверка открытости формата. (3) Запускается одноразовым контейнером без постоянного сервиса: на машине с ограниченной RAM это важно (во время работы Spark Trino останавливался). Для этой задачи Spark лучше Doris/StarRocks: те быстрее на интерактивной аналитике, но это ещё один постоянно работающий сервер (FE + BE) с собственным хранилищем — избыточно при 3,6 ГБ памяти и дублирует роль Trino. |

**Скрипт развёртывания.** Скачивание jar'ов Iceberg (один раз) и конфиг `spark/spark-defaults.conf` (в репозитории):

```powershell
mkdir spark\conf, spark\jars -Force | Out-Null
curl.exe -fsSL -o spark\jars\iceberg-spark-runtime-3.5_2.12-1.7.1.jar https://repo1.maven.org/maven2/org/apache/iceberg/iceberg-spark-runtime-3.5_2.12/1.7.1/iceberg-spark-runtime-3.5_2.12-1.7.1.jar
curl.exe -fsSL -o spark\jars\iceberg-aws-bundle-1.7.1.jar https://repo1.maven.org/maven2/org/apache/iceberg/iceberg-aws-bundle/1.7.1/iceberg-aws-bundle-1.7.1.jar

docker stop trino   # освобождаем память на время работы Spark
docker run --rm `
  -v "${PWD}\spark\conf:/opt/spark/conf" `
  -v "${PWD}\spark\jars:/opt/spark/iceberg-jars" `
  -v "${PWD}\p1\sql:/opt/sql" `
  apache/spark:3.5.3 `
  /opt/spark/bin/spark-sql --driver-memory 1g -f /opt/sql/08_spark_bronze.sql
docker start trino
```

Ключевые строки конфига: каталог `bronze` = `org.apache.iceberg.rest.RESTCatalog` с `uri = http://host.docker.internal:8181/catalog`, `warehouse = bronze`; `io-impl = S3FileIO` + `s3.endpoint` MinIO (без этого Spark пытается читать `s3://` через Hadoop и падает с `No FileSystem for scheme "s3"`). Jar'ы монтируются в отдельную папку `/opt/spark/iceberg-jars`, чтобы не затереть собственные библиотеки Spark в `/opt/spark/jars`.

**Действия и результат** (скрипт `sql/08_spark_bronze.sql`, вывод консоли):

| Действие в Spark | Результат | Время |
|---|---|---|
| `SHOW TABLES IN bronze.q10` | `nation`, `customer`, `orders`, `lineitem` — Spark видит таблицы, созданные Trino | 3,86 с (включая инициализацию каталога) |
| `SELECT count(*) FROM bronze.q10.lineitem` | 6 001 215 — совпадает с Trino | 4,22 с |
| `SELECT ... FROM bronze.q10.lineitem.snapshots` | 1 снапшот, операция `append` — тот, что записал Trino; Spark читает метаданные Iceberg | 0,53 с |
| Q10 на `bronze.q10.*` | 20 строк, первый — `Customer#000057040`, JAPAN, 734 235,2455 — **совпадает с Gold**, построенным Trino | 6,87 с |

Сравнение движков на Q10 по Bronze (ZSTD): Trino — 6,87 с холодный / 3,3–4,0 с тёплый (с учётом старта CLI); Spark — 6,87 с (время самого запроса, первый в сессии, без учёта ~15 с старта JVM и контейнера). Trino выигрывает на интерактивных одиночных запросах за счёт мгновенного старта; Spark окупается на длинных пайплайнах и больших объёмах.

## 7. Выводы

Медальон разделяет ответственность: Bronze хранит неизменную копию источника (из неё восстанавливается всё остальное), Silver — очищенные, нормализованные и обогащённые данные, пригодные для многих отчётов, Gold — маленькую готовую витрину (20 строк, 3,4 КБ), корректность которой подтверждена сравнением с эталонным Q10 (20/20 совпадений). Партиционирование надо выбирать под шаблон запросов и объём: `year(orderdate)` на Silver дал отсечение 3 из 4 файлов, а мелкие таблицы партиционировать вредно. Бенчмарк показал, что сжатие ускоряет, а не замедляет аналитику: ZSTD уменьшил Bronze в 2,6 раза, записывал быстрее всех и дал самый быстрый Q10 — поэтому он выбран для всех слоёв вместо GZIP (на 3 % компактнее, но в 1,7 раза медленнее на записи) и SNAPPY (на 38 % больше). Iceberg поверх объектного хранилища дал свойства базы данных — эволюцию схемы без перезаписи файлов, time travel и откат ошибки за одну команду — и при этом открытость: те же таблицы без копирования прочитал второй движок (Spark).
